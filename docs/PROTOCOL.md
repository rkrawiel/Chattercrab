# Chattercrab Signaling Protocol

Version 1. All types are defined in the `chattercrab-protocol` crate; this document is the
human-readable specification. The server listens on `CHATTERCRAB_BIND` (default
`0.0.0.0:8443`) and serves HTTPS and WSS when a certificate is configured, plain HTTP and
WS otherwise (local development only).

## 1. Common types

| Type | JSON | Rules |
|------|------|-------|
| `RoomId` | string | 1 to 64 characters from `[A-Za-z0-9_-]`. Generated by the server (12 lowercase alphanumerics). |
| `RoomName` | string | Trimmed, 1 to 48 characters, no control characters. |
| `PeerId` | string | UUID v4, lowercase hyphenated, e.g. `"3f2b8c1e-9d4a-4f6e-8b7a-2c1d0e9f8a7b"`. Assigned by the server on join. Ordering is plain string (byte) ordering. |
| `DisplayName` | string | Trimmed, 1 to 32 characters (Unicode scalar values), no control characters. |
| `Timestamp` | integer | Milliseconds since the Unix epoch, UTC. |

`PeerInfo`:

```json
{ "id": "3f2b8c1e-9d4a-4f6e-8b7a-2c1d0e9f8a7b", "display_name": "ada" }
```

`ChatMessage`:

```json
{
  "id": 17,
  "from": "3f2b8c1e-9d4a-4f6e-8b7a-2c1d0e9f8a7b",
  "display_name": "ada",
  "text": "hello",
  "ts": 1793875200000
}
```

`id` increases monotonically within a room. `text` is 1 to 2000 characters after trimming.

`ErrorCode` (snake_case string):

| Code | Meaning |
|------|---------|
| `bad_request` | Malformed JSON, unknown message type, or invalid field. |
| `invalid_display_name` | Display name failed validation. |
| `invalid_room_name` | Room name failed validation. |
| `chat_too_long` | Chat text empty or longer than 2000 characters. |
| `room_not_found` | No room with that id. |
| `room_full` | Room already has `CHATTERCRAB_MAX_ROOM_SIZE` members. |
| `max_rooms` | Server already hosts `CHATTERCRAB_MAX_ROOMS` rooms. |
| `rate_limited` | Too many requests from this IP. |
| `unauthorized` | Missing or incorrect HTTP Basic credentials. |
| `join_timeout` | No `join` within 5 seconds of connecting. |
| `not_joined` | A message other than `join` was sent before joining. |
| `already_joined` | A second `join` on the same socket. |
| `peer_not_found` | The `to` peer is not in the room. |
| `not_screen_publisher` | `screen_stop` from a peer that is not publishing. |
| `internal` | Unexpected server error. |

`ApiError` (REST error body):

```json
{ "code": "room_full", "message": "room is full (5 members)" }
```

## 2. REST endpoints

All bodies are `application/json`. Request bodies are limited to 16 KiB.

### Authentication

When `CHATTERCRAB_PASSWORD` is set (after trimming), every endpoint except `GET /health`
requires HTTP Basic authentication. An empty or unset password disables the check.
`GET /health` is always open. A CORS preflight (`OPTIONS`) does not require credentials.

```http
Authorization: Basic base64(user:password)
```

The user is `CHATTERCRAB_AUTH_USER` (default `chattercrab`). The user must not contain
`:`. The password may. A missing header, wrong scheme, bad base64, bad UTF-8, wrong
user, or wrong password is the same response: `401 Unauthorized`,
`WWW-Authenticate: Basic realm="chattercrab"`, and

```json
{ "code": "unauthorized", "message": "unauthorized" }
```

The body does not say whether the user or the password was wrong. An authenticated
`GET /ws/{room_id}` for an unknown room is still `404`. Without valid credentials that
upgrade is `401`.

### `GET /health`

```json
{ "status": "ok", "version": "0.1.0" }
```

### `GET /rooms`

`200 OK`, array of `RoomSummary` sorted by `created_at` ascending:

```json
[
  { "id": "k3v9q2m7x1ab", "name": "standup", "member_count": 3, "created_at": 1793875200000 }
]
```

### `POST /rooms`

Request `CreateRoomRequest`:

```json
{ "name": "standup" }
```

| Status | Body |
|--------|------|
| `201 Created` | `RoomSummary` with `member_count: 0` |
| `400 Bad Request` | `ApiError` `invalid_room_name` / `bad_request` |
| `429 Too Many Requests` | `ApiError` `rate_limited` (default 10 creations per minute per IP, burst 5) |
| `503 Service Unavailable` | `ApiError` `max_rooms` |

A room that nobody joins is evicted after `CHATTERCRAB_ROOM_IDLE_TTL_SECS`. A room is
deleted immediately when its last member leaves.

### `GET /ice-servers`

Returns the single STUN URL configured on the server (`CHATTERCRAB_STUN_URL`, default
`stun:stun.l.google.com:19302`). There is no TURN relay and no credential. The body is
`IceServers` and contains only `urls`.

```json
{ "urls": ["stun:stun.l.google.com:19302"] }
```

| Status | Body |
|--------|------|
| `200 OK` | `IceServers` |
| `429 Too Many Requests` | `ApiError` `rate_limited` (default 30 per minute per IP; the message says too many ICE server requests) |

### `GET /ws/{room_id}`

WebSocket upgrade. Returns `404` with `ApiError` `room_not_found` if the room does not exist
at upgrade time, and `503` with `ApiError` `internal` while the server is shutting down.
Frames are UTF-8 JSON text frames, one message per frame, at most 64 KiB.
Binary frames are rejected with `bad_request`.

## 3. WebSocket messages

Every message is a JSON object with a `t` field naming the variant (snake_case).
Unknown fields are ignored; unknown `t` values are `bad_request`.

### 3.1 Client to server

#### `join`

Must be the first message, within 5 seconds.

```json
{ "t": "join", "display_name": "ada" }
```

#### `offer` / `answer`

```json
{ "t": "offer", "to": "8c1d...", "sdp": "v=0\r\no=- 4611... 2 IN IP4 127.0.0.1\r\n..." }
```

```json
{ "t": "answer", "to": "3f2b...", "sdp": "v=0\r\n..." }
```

#### `ice`

Trickle ICE candidate. `candidate` has the same format as `RTCIceCandidateInit.candidate`
(the SDP attribute without the leading `a=`).
`sdp_mid` and `sdp_mline_index` are optional. An empty `candidate` string signals
end-of-candidates.

```json
{
  "t": "ice",
  "to": "8c1d...",
  "candidate": "candidate:1 1 udp 2130706431 192.168.1.20 50214 typ host",
  "sdp_mid": "0",
  "sdp_mline_index": 0
}
```

#### `chat`

```json
{ "t": "chat", "text": "hello" }
```

#### `screen_request` / `screen_stop`

```json
{ "t": "screen_request" }
```

```json
{ "t": "screen_stop" }
```

#### `ping`

Application-level keepalive and RTT probe; the server answers `pong`. Independent of the
WebSocket-level Ping/Pong heartbeat described in section 4.

```json
{ "t": "ping" }
```

### 3.2 Server to client

#### `welcome`

Reply to `join`. `peers` excludes the receiver. `history` holds up to the last 200 chat
messages, oldest first.

```json
{
  "t": "welcome",
  "you": "3f2b8c1e-9d4a-4f6e-8b7a-2c1d0e9f8a7b",
  "peers": [ { "id": "8c1d0e9f-...", "display_name": "grace" } ],
  "history": [ { "id": 16, "from": "8c1d0e9f-...", "display_name": "grace", "text": "hi", "ts": 1793875190000 } ],
  "screen_publisher": null
}
```

#### `peer_joined` / `peer_left`

```json
{ "t": "peer_joined", "peer": { "id": "3f2b...", "display_name": "ada" } }
```

```json
{ "t": "peer_left", "peer_id": "3f2b..." }
```

#### `offer` / `answer` / `ice`

Relayed verbatim with `from` replacing `to`:

```json
{ "t": "offer", "from": "3f2b...", "sdp": "v=0\r\n..." }
```

```json
{ "t": "answer", "from": "8c1d...", "sdp": "v=0\r\n..." }
```

```json
{ "t": "ice", "from": "3f2b...", "candidate": "candidate:...", "sdp_mid": "0", "sdp_mline_index": 0 }
```

#### `chat`

```json
{ "t": "chat", "msg": { "id": 17, "from": "3f2b...", "display_name": "ada", "text": "hello", "ts": 1793875200000 } }
```

#### Screen arbitration

```json
{ "t": "screen_granted" }
```

```json
{ "t": "screen_denied", "reason": "grace is already sharing" }
```

```json
{ "t": "screen_started", "publisher": "3f2b..." }
```

```json
{ "t": "screen_stopped" }
```

`screen_started` and `screen_stopped` go to every member, including the publisher.
A repeated `screen_request` from the current publisher is answered with `screen_granted`
and no broadcast.

#### `error`

```json
{ "t": "error", "code": "peer_not_found", "message": "peer 8c1d... is not in this room" }
```

#### `pong`

```json
{ "t": "pong" }
```

## 4. Connection lifecycle

1. Client opens `wss://host:8443/ws/{room_id}`.
2. Client sends `join` within 5 s. Otherwise: `error{join_timeout}`, close `1008`.
3. Room full: `error{room_full}`, close `1008`. Invalid name: `error{invalid_display_name}`, close `1008`.
4. Server sends `welcome` and broadcasts `peer_joined` to the others.
5. Heartbeat: the server sends a WebSocket Ping every 20 s. Two consecutive unanswered
   Pings close the socket (`1011`). Standard WebSocket clients answer automatically.
6. Each connection has a server-side outbound queue of 256 messages. If it fills the
   server drops the connection (close `1008`, reason `slow consumer`).
7. On disconnect the server broadcasts `peer_left`, and `screen_stopped` if the leaver was
   the screen publisher. The room is deleted when it becomes empty.
8. Server shutdown: every socket receives close `1001` (going away).

Non-fatal errors (`bad_request` after join, `peer_not_found`, `chat_too_long`,
`not_screen_publisher`, `already_joined`) are reported with `error` and the socket stays open.

## 5. Close codes

| Code | When |
|------|------|
| `1000` | Normal close requested by the client. |
| `1001` | Server shutting down. |
| `1008` | Policy: join timeout, protocol violation before join, room full, slow consumer. |
| `1011` | Heartbeat failure. |
